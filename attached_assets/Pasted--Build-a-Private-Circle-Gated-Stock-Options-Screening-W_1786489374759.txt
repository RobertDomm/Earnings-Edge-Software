# Build a Private Circle-Gated Stock & Options Screening Web Application

Build a production-quality full-stack web application for a client who operates a private community using Circle.

The application will eventually analyze live stock and options market data and run a specific set of filters to identify stocks that meet the client's criteria for potential options trades.

The detailed stock/options filtering strategy will be provided later.

For this first phase, focus on:

1. Secure Circle authentication and Space Group authorization
2. Preventing unauthorized access through copied/shared links
3. Building the stock/options dashboard
4. Creating the architecture for live market data
5. Creating a modular stock/options screening engine
6. Using mock market data until the real data provider and filtering criteria are supplied

---

# 1. CRITICAL ACCESS REQUIREMENT

This application is exclusively for members of the client's Circle community who have access to ONE SPECIFIC CIRCLE SPACE GROUP.

Being a member of the overall Circle community is NOT sufficient.

The authorization rule must be:

**Authenticated Circle Member + Access to Required Space Group = ACCESS GRANTED**

**Authenticated Circle Member + No Access to Required Space Group = ACCESS DENIED**

**Not Authenticated Through Circle = ACCESS DENIED**

The specific Circle Space Group will be configured later.

Circle must remain the source of truth for determining whether someone is authorized to use this application.

---

# 2. NO SEPARATE APP LOGIN

Do NOT create a traditional authentication system for this application.

Users should NOT:

* Create an account for this app
* Create another username
* Create another password
* Register separately
* Manually log into the application every time

The intended user experience is:

**User logs into Circle → User enters authorized Space Group → User launches application → App verifies Circle authorization → Dashboard opens**

The authorization process should happen automatically and securely behind the scenes.

The application can maintain a secure server-side session after Circle authorization has been verified.

---

# 3. SHARING THE APPLICATION URL MUST NOT GRANT ACCESS

This requirement is extremely important.

Do NOT protect this application simply by placing its URL inside a private Circle Space Group.

Assume that authorized users will eventually discover the direct application URL.

Someone must NOT gain access simply because an authorized user copies the URL and sends it to them.

Example:

### Authorized User

User is logged into Circle.

User has access to the required Space Group.

User opens the application.

Result:

**ACCESS GRANTED**

### Circle Member Without Space Group Access

User has a valid Circle account.

User belongs to the client's Circle community.

User does NOT have access to the required Space Group.

User obtains the application's direct URL from another member.

Result:

**ACCESS DENIED**

### Non-Circle User

Person is not an authorized member of the client's Circle community.

Someone sends them the direct application URL.

They open it.

Result:

**ACCESS DENIED**

Therefore:

**The URL itself must NEVER act as the authorization mechanism.**

---

# 4. SERVER-SIDE AUTHORIZATION

All meaningful authorization must happen on the backend.

Do NOT rely on:

* Secret URLs
* Hidden URLs
* Frontend JavaScript
* An iframe by itself
* LocalStorage authorization flags
* SessionStorage authorization flags
* URL query parameters such as `?authorized=true`
* Referrer headers as the primary security mechanism
* Hiding buttons
* Hiding navigation
* Obfuscated frontend code
* A password shared among Circle members

Frontend restrictions are not security.

The backend must independently determine whether the user is authorized.

---

# 5. CIRCLE AUTHORIZATION SERVICE

Create a dedicated authorization module/service.

For example:

`CircleAuthService`

This service should be responsible for:

* Verifying the user's Circle identity
* Verifying that the Circle user belongs to the correct community
* Verifying that the user currently has access to the required Circle Space Group
* Rejecting users without Space Group access
* Establishing a secure application session for authorized users
* Revalidating access when appropriate
* Handling expired/invalid authorization
* Handling Circle API/authentication errors safely

Do not tightly couple Circle authentication logic to the stock dashboard.

The Circle authorization layer should be modular so the exact Circle API, SSO, OAuth, JWT, signed-token, or other supported integration method can be configured later.

Use the most secure officially supported Circle integration available for this use case.

Do NOT invent unsupported Circle API endpoints.

If actual Circle integration credentials or documentation are required, clearly identify what information I need to provide.

---

# 6. REQUIRED SPACE GROUP

Create server-side configuration for the Circle Space Group that grants access to this application.

For example:

`CIRCLE_REQUIRED_SPACE_GROUP_ID`

This value should be stored securely using Replit Secrets/environment variables.

Do not hard-code sensitive Circle information into frontend JavaScript.

The authorization logic should effectively perform:

`Is this a valid Circle member?`

AND

`Does this Circle member currently have access to CIRCLE_REQUIRED_SPACE_GROUP_ID?`

If BOTH conditions are true:

**Allow access.**

Otherwise:

**Deny access.**

---

# 7. ACCESS REVOCATION

Circle should remain the source of truth.

If the client removes someone from the authorized Space Group, that user must also lose access to this application.

Do not permanently authorize someone simply because they successfully accessed the application once.

Use an appropriate secure session expiration/revalidation strategy.

For example, authorization can be cached for a reasonable short period for performance, but the application should periodically revalidate Space Group access.

Do not make the session unnecessarily long-lived.

# 22. SECURITY REQUIREMENTS

Follow standard web application security practices.

At minimum:

* Keep secrets server-side.
* Use secure environment variables.
* Protect backend endpoints.
* Validate inputs.
* Use secure session cookies where applicable.
* Use HttpOnly cookies where appropriate.
* Use Secure cookies in production.
* Use appropriate SameSite settings based on the final Circle launch/embed architecture.
* Protect against CSRF where applicable.
* Avoid exposing stack traces.
* Avoid logging authentication tokens.
* Never put private API keys into frontend code.
* Never trust frontend authorization claims.
* Never trust URL parameters as proof of authorization.
* Validate Circle authorization server-side.
* Validate required Space Group access server-side.

# 32. MOST IMPORTANT RULE

The fundamental security model for this application is:

**CIRCLE MEMBERSHIP ALONE DOES NOT GRANT ACCESS.**

The user MUST have access to the specifically configured Circle Space Group.

Think of the required Circle Space Group as the application's permission group.

Circle remains responsible for deciding who belongs to that group.

The Replit application is responsible for securely verifying that permission before granting access.

A direct URL must never bypass this requirement.

# 33. DEFINITION OF SUCCESS FOR VERSION 1

Version 1 is successful when:

1. The application has a professional stock/options scanner dashboard.
2. Mock stock/options data is displayed.
3. A modular screening engine exists.
4. Individual filtering rules can easily be added later.
5. Circle authentication is isolated into a dedicated service.
6. Access requires membership in the designated Circle Space Group.
7. Ordinary Circle members without that Space Group cannot access the application.
8. Non-Circle visitors cannot access the application.
9. Sharing the direct application URL does not grant authorization.
10. Protected backend endpoints cannot be accessed without authorization.
11. Mock authentication allows development before real Circle credentials are connected.
12. The project clearly documents what information is required to activate real Circle authentication.
13. The architecture is ready for a live stock/options market-data provider.
14. No real trading strategy is invented.
15. No brokerage/trade-execution functionality is implemented.

Before making assumptions about Circle's current authentication/API capabilities, stop and identify what information or credentials are needed from me.

Do not weaken the security model just to make the prototype easier to build.

The final production application must use Circle authentication plus verification of access to the specifically designated Circle Space Group as the gatekeeper for the entire stock/options application.
